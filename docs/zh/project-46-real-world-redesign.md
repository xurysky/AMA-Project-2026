# 46 号项目真实场景重设计

## 1. 重新定位

原来的系统更像一个理想化的“全渠道 AI 零售大脑”：它能讲清楚 Agent、Customer 360、动态定价、营销自动化和区域合规，但真实企业里不会一上来允许 AI 自动改价、自动调拨、自动触达客户。

更现实的定位应该是：

**零售异常处理与经营决策 Copilot**

它不是替代 ERP、WMS、OMS、CRM、CDP 或营销自动化平台，而是在这些系统之上做三件事：

1. 从已有系统里发现经营异常。
2. 给业务负责人生成可解释的决策包。
3. 把审批后的动作转成下游系统可执行的工单、任务或 API 调用。

一句话表达：

> 当门店、库存、会员、天气和销售数据出现异常时，系统帮助区域运营、商品、供应链、CRM 和合规团队更快完成“看见问题、判断原因、形成动作、留下审计”的闭环。

## 2. 真实业务场景

### 场景名称

**上海区域夏季热浪下的 AIRism 缺货风险与反季库存处理**

### 背景

一家亚洲服装零售商在上海有 38 家门店。7 月初连续高温，AIRism、速干、防晒、儿童透气类 SKU 销售突然上升。同时，部分门店仍有春季薄外套和冬季 HEATTECH 尾货，占用仓储和陈列空间。

真实业务里，问题不会表现为“全渠道 Agent 自动优化一切”，而是表现为几个很具体的运营异常：

- 12 家门店 AIRism 主推尺码只够卖 1.5 天。
- 华东仓还有 8,400 件可补货，但补到上海核心门店至少需要 36 小时。
- 3 家郊区门店 AIRism 销售没起来，不适合继续补货。
- 春季薄外套库存周转变慢，但直接大折扣会冲击毛利。
- CRM 想触达高意向会员，但只能触达已同意营销的用户。
- 门店店长更关心“明天上午能不能到货”，不是宏观 AI 架构。

### 目标

系统目标从夸张的“销售 +40%、LTV +60%”调整为更可信的运营目标：

- 缺货风险门店在 24 小时内生成补货或跨店调拨建议。
- 高风险 SKU 的人工判断时间从 2 小时降到 20 分钟。
- 营销触达只覆盖已授权用户，且不推荐不可履约商品。
- 反季 SKU 折扣必须受毛利底线和审批权限约束。
- 每个建议都能追溯到数据来源、规则、Agent 推理和人工审批人。

## 3. 用户角色

系统的真实用户不是消费者，而是零售企业内部经营团队。

- 区域运营经理：决定哪些门店优先补货、是否跨店调拨。
- 商品经理：判断 SKU 生命周期、陈列优先级和折扣边界。
- 供应链计划员：确认仓库可用库存、运输时效和补货批次。
- 门店店长：确认本店实际陈列、客流和尺码断码情况。
- CRM 经理：审批会员触达策略、渠道和优惠券预算。
- 合规/风控：检查营销授权、数据脱敏、审批权限和审计记录。

## 4. 系统边界

### 系统负责

- 聚合 POS、库存、天气、CRM、商品主数据和营销数据。
- 识别缺货、滞销、异常折扣、履约不可达等经营异常。
- 生成补货、调拨、降价、触达和人工复核建议。
- 显示证据、置信度、风险原因和审批路径。
- 保存 run、工单、审批、执行回执和审计日志。

### 系统不负责

- 不直接替换 SAP/ERP 的库存主账。
- 不直接自动修改生产价格。
- 不绕过 CRM/CDP 做客户触达。
- 不承诺原型已经证明销售大幅提升。
- 不处理真实 PII，Demo 只使用合成数据。

## 5. 业务流程

### 早晨 7:30：经营异常生成

系统从昨晚到当前的数据中生成区域异常清单：

- AIRism 男款 M/L 码库存覆盖低于 2 天。
- 三家旗舰店 App 收藏和到店试穿升高，但门店库存不足。
- 两家门店库存充足但动销慢，适合跨店调拨。
- 春季外套库存周转低于阈值，建议小范围会员券，不建议全场降价。

### 8:00：业务负责人打开工作台

工作台默认不是“宏大 Control Tower”，而是待处理队列：

- 需要今天处理的异常。
- 每个异常影响哪些门店和 SKU。
- 推荐动作是什么。
- 哪些动作需要谁审批。
- 哪些数据不完整，需要人工确认。

### 8:15：Agent 生成决策包

Agent 不直接执行动作，而是形成结构化建议：

- Inventory Agent：建议从低动销门店和华东仓给 12 家门店补 2,600 件。
- Pricing Guardrail Agent：AIRism 不打折，春季外套允许 15% 会员券，超过 20% 需要财务审批。
- Customer Eligibility Agent：筛出 18,420 名已授权且近 14 天有相关浏览/收藏/加购行为的会员。
- Store Ops Agent：列出需要店长确认的断码和陈列位置。
- Compliance Agent：标记营销授权、数据脱敏、审批权限和审计是否满足要求。

### 8:30：人工审批

系统把动作分成三类：

- 可执行：低风险补货、库存查询、店长确认任务。
- 需审批：跨店调拨、会员券、营销触达。
- 阻断：未授权客户触达、低毛利折扣、不可履约推荐。

### 9:00：写入下游系统

审批完成后，系统把动作转成下游系统的任务：

- WMS/ERP：生成补货建议单或调拨申请。
- 门店任务系统：生成陈列检查和断码确认任务。
- CRM/CDP：创建已授权人群包和活动草稿。
- Power BI/Fabric：记录后续销量、缺货率、折扣毛利和转化结果。

## 6. Agent 重新设计

真实系统里，Agent 应该更像“能力模块”，而不是人格化角色。

### 1. Exception Detection Agent

发现异常，不做最终决策。

输入：

- POS 销售、库存快照、天气、活动日历、商品生命周期、门店等级。

输出：

- 异常类型、影响范围、优先级、缺失数据。

### 2. Inventory & Fulfillment Agent

关注能不能卖、能不能补、什么时候到。

输出：

- 门店库存覆盖天数。
- 仓库可用库存。
- 跨店调拨候选。
- ETA 和履约风险。

### 3. Pricing & Margin Guardrail Agent

关注折扣是否合理，而不是动态改价。

输出：

- SKU 毛利底线。
- 可用折扣区间。
- 审批级别。
- 禁止动作。

### 4. Customer Eligibility Agent

关注哪些客户可以被触达。

输出：

- 已授权用户规模。
- 高意向用户分层。
- 不可触达人群剔除原因。
- 渠道限制。

### 5. Decision Packet Agent

把多个 Agent 的结果变成业务能看懂的决策包。

输出：

- 推荐动作。
- 证据。
- 风险。
- 审批人。
- 下游执行系统。

### 6. Compliance & Audit Agent

只做门禁和留痕。

输出：

- PASS / PASS_WITH_FLAGS / BLOCKED。
- 阻断原因。
- 审计字段完整性。
- 是否包含 PII。

## 7. 数据架构

### Demo 阶段

- Azure Container Apps：FastAPI 运行时和 UI。
- Cosmos DB：run、工单、审批、审计日志。
- Azure OpenAI：生成解释、行动摘要和营销草稿。
- 合成 JSON/CSV：模拟 POS、库存、会员授权、门店和天气数据。

### 生产阶段

- Event Hubs：接收 POS、库存、OMS、CRM、天气和营销事件。
- Microsoft Fabric：统一历史数据、BI、特征计算和 KPI 回流。
- Cosmos DB：低延迟运行状态、工单状态和审计。
- Azure AI Search：商品政策、促销规则、运营 SOP、合规政策检索。
- APIM / Logic Apps / Functions：连接 ERP、WMS、CRM、CDP、门店任务系统。
- Key Vault / Managed Identity / Private Link：企业安全边界。
- Application Insights：Agent 决策链路、失败率、延迟和人工覆盖率。

## 8. UI 重新设计

第一屏不再展示宏观愿景，而是一个真实工作台：

### 1. 今日异常队列

- 缺货风险
- 调拨机会
- 滞销库存
- 会员触达机会
- 合规阻断

### 2. 决策包详情

每个异常点开后显示：

- 影响门店和 SKU。
- 建议动作。
- 数据证据。
- 预计影响。
- 风险和限制。
- 审批链路。

### 3. 执行队列

- 待审批
- 可执行
- 已发送下游系统
- 执行失败
- 已完成

### 4. 审计视图

- 哪个 Agent 提出建议。
- 用了哪些数据。
- 谁审批。
- 什么时候发送到哪个系统。
- 结果如何回流。

## 9. 评审时的可信说法

推荐用这个表述：

> 这个项目不是要证明 AI 可以完全自动经营零售，而是证明在复杂零售场景中，AI Agent 可以作为“异常识别 + 决策准备 + 审批协同 + 执行留痕”的中间层，帮助企业把原本分散在 Excel、邮件、ERP、CRM 和人工会议里的判断流程结构化、可追溯、可度量。

避免说：

- AI 自动完成全渠道经营。
- 已经实现销售 +40%。
- Agent 可以自动决定价格。
- Customer 360 能无条件跨区域使用。

可以说：

- Demo 使用目标假设和合成数据验证架构可行性。
- 生产系统需要通过 test/control 门店验证 KPI。
- 高风险动作需要人工审批。
- AI 的价值先从减少判断时间、减少漏处理、提升执行一致性开始。

## 10. 建议的 Demo 改造方向

保留现有 Azure 部署和 5 Agent 技术基础，但把前端和场景重心改成：

- 默认打开“今日异常队列”，不是平台介绍页。
- 把一个 run 改成一个真实异常处理单。
- 每个 Agent 输出都绑定到业务字段：SKU、门店、库存覆盖天数、毛利、授权用户数、审批人。
- GPT 生成内容从“营销文案炫技”改成“业务摘要、审批说明、门店任务说明、CRM 活动草稿”。
- KPI 从大目标改成过程指标：处理时长、审批通过率、缺货风险减少、折扣毛利守住、不可触达人群剔除数。

这样系统会更像企业内部真的会买单的应用，而不是一个为了比赛而拼出来的理想化 AI 平台。
